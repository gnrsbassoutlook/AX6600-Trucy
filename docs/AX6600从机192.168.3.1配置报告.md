
**备份**：`/etc/opkg/distfeeds.conf.bak.1790486861`

## 4. ③ AdGuard Home + OAF 联动策划（核心）

### 4.1 先纠正一个概念：ADH 和 OAF **不是"谁在上游谁在下游"的关系**

它们是**两个不同层面**的过滤，各自独立工作，可以叠加：

|          | **AdGuard Home (ADH)** | **OAF 行为管理**                                |
| -------- | ---------------------- | ------------------------------------------- |
| 工作层面     | **DNS 层**（域名解析）        | **流量层**（DPI 深度包检测，第 4~7 层）                  |
| 判据       | 域名                     | 应用特征 / L7 载荷 / HTTPS SNI                    |
| 拦什么      | 色情/成人/广告/恶意**网站**      | **具体 App**（王者、抖音、YouTube…）、上网时段、按设备         |
| 是否依赖 DNS | 是（核心）                  | **否**（官方明确：*operates independently of DNS*） |
| 性能开销     | 很轻                     | 较重（逐流解析）                                    |

**真正的"上下游"只存在于 DNS 链里**，现在是：

```
客户端(孩子设备)
   │  DNS 查询
   ▼
dnsmasq :53 (从机)          ← 局域网唯一 DNS 入口，负责 DHCP + 本地域名
   │  server=127.0.0.1#5335（noresolv=1）
   ▼
AdGuard Home :5335          ← 在这里做"色情/广告域名"拦截 ★
   │  未命中过滤 → 转发上游
   ▼
上游：192.168.1.1(主机) / 223.5.5.5 / 119.29.29.29
   │  （走主机既保证了主机的梯子分流逻辑不变，又有公共DNS兜底）
   ▼
Internet
```

OAF 则是在**转发路径上旁路抓包**，与上面这条 DNS 链**平行**，互不干扰。

### 4.2 建议的分工（就这么用）

- **ADH 管"内容"**：色情 / 成人 / 广告 / 恶意站点 → 全屋统一，DNS 层拦，开销小。
- **OAF 管"应用与时间"**：只针对**孩子那一台设备**（用 MAC 或用户模式加规则），限制游戏/短视频/上网时段。
- **不要在 OAF 上做全屋全量 App 拦截**——那是它卡的主因（见 4.4）。

### 4.4 为什么 OAF 会特别卡 + 优化建议

1. **DPI 与硬件加速天然冲突**：OAF 要逐流解析才能识别应用，这会削弱 NSS/HNAT 硬件转发加速，流量越大量越明显。
2. **本固件同时在 rc.d 里 enable 了一堆"打架"的插件**：`adbyby`、`koolproxy`(去广告) + `mosdns`、`smartdns`(DNS) + `openclash`、`passwall`(代理)。它们大多**根本没启动成功**，却仍在增加开机负担与潜在冲突。
3. **建议动作（可按需执行）**：
   - OAF 只对孩子的设备加规则（用 **MAC 过滤 / 用户模式**），不要全屋全量。
   - **停用与 ADH 重复的去广告插件**：`adbyby`、`koolproxy`（见第 5 节）。
   - **代理栈只留一个**（你现在实际一个都没跑；如果不需要在从机上翻墙，建议把 `openclash/passwall/ssr-plus` 的自启也关掉，靠主机出网即可）。
   - `fwx` 里 `disable_hnat=0` 保持不动（别关硬件加速）。

### 4.5 关于"广告屏蔽大师 Plus+"（= `luci-app-adbyby-plus`）

**它不是 ADH 的综合加强版**，而是**另一条独立路子**：

- 老的去广告方案：**HTTP 透明代理**（劫持 80 端口）+ hosts，主要对付网页广告；
- 不擅长 HTTPS / App 内外广告，也不适合做家长控制；
- 与 ADH 功能**重叠且性能更差**，两者同时开只会更卡。

**结论：建议停用 adbyby，统一交给 ADH。**（它当前也没真正跑起来。）

**→ 从机的 OAF 插件已是官方最新版 v7.0.1（2026-08-29 发布），比主机还新，没有可升的版本。**

### 为什么 iPhone 上还是提示"没安装家长控制插件/版本过低"

最可能是这两个原因之一（不是配置问题）：

1. **iOS 端 App 版本滞后于插件**。OAF 官网明确写过：*"v6.1.7 已发布，但 iOS App 还在审核，iOS 端目前只支持管理 v6.1.6 及更早版本"*。你的插件是 7.0.1，手机 App 若不认识新版本就会报这个错。  
   → **先去 App Store 把 OPAssistant 更新到最新**，大概率就好。
2. **App 的"家长控制"需要官方 OpenWrt 固件配套**（提示里那句"或者升级官方固件"就是这么来的）。bleachwrt 属于第三方固件，官方对此"不做技术支持"。

### 那条"OAF ACL 插件"是什么意思

OAF 从 **6.1.5** 起就加入了 ACL / RPC 相关能力（"Add rpc acl file"），到 v7.x 已经内建完整的 用户/白名单/MAC过滤/仪表盘。**你的 7.0.1 已经包含这些，不需要额外装 ACL 插件**——那句话是给"还停在 6.1.3~6.1.4"的人看的。

### 硬限制：内核模块升级不了（重要）

- `kmod-oaf` 的**内核模块内部版本是 6.0.1**（守护进程是 7.0.1）。
- 上游 7.0.1 提供的内核包是给 **OpenWrt 25.12.5 / 内核 6.12.94** 编译的；你这台是 **内核 6.12.93** 的 bleachwrt 定制内核，`vermagic` 不符，**模块装载会失败**，强行装会有风险。
- 所以"内核模块级"的对齐只能靠**固件作者出新版固件**。在现有固件上，**用路由器自带的"OAF 行为管理"网页（LuCI）功能是完全正常的**，只是手机 App 的"家长控制"这一入口受 App 版本制约。

**建议顺序**：① 更新 iPhone 上的 OPAssistant → ② 还不行就直接用 LuCI 里的 OAF 页面（功能一模一样）。

## 10. iPhone 专项调优 + 防 DNS 绕过（2026-09-27 追加）

**目标**：iPhone（`192.168.3.121`，从机 DHCP）能正常用 GitHub / YouTube，Pornhub / jable.tv 被拦。

### 查出的两个真问题

**问题 1 —— ADH 上游混了国内 DNS（这是 YouTube 卡顿的真凶）**

原配置 `upstream_dns: [192.168.1.1, 223.5.5.5, 119.29.29.29]` + `upstream_mode: parallel`（并行取最快）。
`223.5.5.5` / `119.29.29.29` 对 YouTube 这类域名会返回**伪造 IPv6 地址**（实测 `2001::1`、`2001::6ca0:a58d`）。
iPhone 优先走 IPv6 → 撞上假地址 → 连接卡住后才回落 IPv4，表现为"**YouTube 打不开 / 很慢**"。

**问题 2 —— 本网络根本没有全局 IPv6**

从机只有 ULA（`fdbc:` / `fd7f:`）和链路本地地址；`ping6` 全部失败，`curl -6 youtube` 返回 `000`。
在这种网络里给客户端下发真实的 Google AAAA 记录**纯属有害**（只能造成回落延迟）。

### 已做的修正

| 项目 | 改前 | 改后 |
|---|---|---|
| `dns.upstream_dns` | `192.168.1.1` + 2 个国内 DNS | **只留 `192.168.1.1`**（带梯子的主机，解析完全正确） |
| `dns.fallback_dns` | `[]` | `223.5.5.5` / `119.29.29.29`（**仅上游失败时兜底**） |
| `dns.aaaa_disabled` | `false` | **`true`**（彻底消除假 IPv6 与回落延迟） |
| `dns.ratelimit_whitelist` | `[]` | `127.0.0.1` / `::1` |
| `user_rules` | 38 条 | **107 条**（新增 69 条：jable 家族 + JAV/国产业余站） |

> **为什么必须放宽限速**：`dnsmasq-upstream` 模式下，dnsmasq 转发查询时**丢掉了真实客户端 IP** ——
> ADH 日志里 326 条查询**全部显示 `127.0.0.1`**。而 `ratelimit: 20` 是按客户端计算的，
> 于是**全屋设备共用一个 20 qps 配额**，忙时会返回 **REFUSED**，表现为随机性的"某些网站突然打不开"。
> ⚠️ 注意：`ratelimit_whitelist` **只接受纯 IP**，写成 `127.0.0.0/8` 会让 ADH 启动失败（`ParseAddr` 报错）。

## 12. ADH 面板登录与"按 IP 限制访问"

### 12.1 登录凭据（实测可用）

| 项 | 值 |
|---|---|
| 地址 | `http://192.168.3.1:3000/login.html` |
| 用户名 | **`root`**（⚠️ **不是 `admin`**，这是最容易卡住的地方） |
| 密码 | 与两台路由器登录/SSH 同一口令 |
| 验证 | `POST /control/login` → **HTTP 200** ✅ |

### 12.2 ADH 图形界面里"能设置的 IP"和"不能设置的 IP"

**✅ 能设**：`设置 → DNS 设置 → 访问设置 → 允许的客户端 / 不允许的客户端`
（对应 YAML：`dns.allowed_clients` / `dns.disallowed_clients`）
- 作用：**限制"哪些客户端可以用 ADH 做 DNS 解析"** —— **和面板登录完全无关**。
- 🔴 **本机绝对不要往里填内网 IP**：我们是 `dnsmasq-upstream` 模式，dnsmasq 转发时**丢掉了真实客户端 IP**，ADH 看到的来源永远是 `127.0.0.1`。一旦填了内网网段当白名单，**全屋 DNS 立刻全部失败**。
  → 此栏**要么留空，要么只填 `127.0.0.1`**。

**❌ 不能设**：ADH **没有**"只允许指定 IP 打开 3000 管理面板"的功能（v0.107.79 二进制实测：无任何 http/面板层 IP 白名单字段）。面板的访问限制必须在**路由器防火墙**上做。

### 12.3 要给面板加 IP 限制，走 LuCI 防火墙

**当前暴露面（实测）**：

| 路径 | 结果 | 说明 |
|---|---|---|
| `http://192.168.3.1:3000` （从 192.168.3.x） | **HTTP 200** | LAN 内任何设备都能打开登录页，需要限制 |
| `http://192.168.1.243:3000` （从 192.168.1.x） | **HTTP 000** | WAN 区 `input=REJECT` 已挡住，无需额外处理 |
| `http://192.168.3.1/` （LuCI 80） | **HTTP 302** | 同理 LAN 内可达 |

**LuCI 路径**：`网络 → 防火墙 → 通信规则 → 添加`，建**两条**（顺序：A 在前，B 在后）

- **规则 A（放行自己）**：名称 `Allow-ADH-Panel`；协议 `TCP`；源区域 `lan`；源地址 `192.168.3.193`（可空格分隔多个，如再加 `192.168.3.121`）；目标区域 `设备（输入）`；目标端口 `3000`；动作 **接受**
- **规则 B（挡住其他人）**：名称 `Deny-ADH-Panel`；协议 `TCP`；源区域 `lan`；**源地址留空**；目标区域 `设备（输入）`；目标端口 `3000`；动作 **拒绝**

> 原理：LAN 区的默认 `input` 是 `ACCEPT`，所以单加一条"接受"不起作用；必须补一条"拒绝"兜底，并让它排在放行规则**之后**。

**等价命令行版（即时生效，不用重启 ADH、不断 DNS）**：
```sh
uci add firewall rule
uci set firewall.@rule[-1].name='Allow-ADH-Panel'
uci set firewall.@rule[-1].src='lan'
uci set firewall.@rule[-1].src_ip='192.168.3.193'
uci set firewall.@rule[-1].proto='tcp'
uci set firewall.@rule[-1].dest='Device'
uci set firewall.@rule[-1].dest_port='3000'
uci set firewall.@rule[-1].target='ACCEPT'

uci add firewall rule
uci set firewall.@rule[-1].name='Deny-ADH-Panel'
uci set firewall.@rule[-1].src='lan'
uci set firewall.@rule[-1].proto='tcp'
uci set firewall.@rule[-1].dest='Device'
uci set firewall.@rule[-1].dest_port='3000'
uci set firewall.@rule[-1].target='REJECT'
uci commit firewall && /etc/init.d/firewall restart
```
回滚：`/etc/init.d/firewall restart` 前先 `uci show firewall | grep -n 'ADH-Panel'` 找到索引，`uci delete firewall.<索引>`。

> ⚠️ **别忘了还有 SSH(22) 和 LuCI(80)**：它们同样是 LAN 全开、且用的是同一个密码。只锁 ADH 面板意义有限 —— 真正的加固是把路由器登录口令改掉，或对 22/80 也做同样的 IP 白名单。

### 12.4 关于 iPhone 的"限制 IP 地址跟踪"（2026-09-27 结论修正）

**你的 iPhone 没有 iCloud+ 订阅 → iCloud 私密代理（Private Relay）在这台设备上根本不存在。**

因此：
- "**限制 IP 地址跟踪**"这个开关**对你**只影响 Apple 邮件隐私保护（Mail Privacy Protection）和 Safari 里对"已知跟踪器"的处理，**不影响 DNS 路径、不影响 ADH 拦截**。
- **开着、关着都对 ADH 没区别**，建议**保持默认开启**（iOS 默认就是开）。
- ⚠️ 我上一轮把它列为"关键绕过源"是**过度归因**：那次 iPhone 变好的真实原因是 **ADH 上游/AAAA 修正 + 过滤表扩容**，与这个开关无关。（`mask.icloud.com` 那套屏蔽手法是给有 iCloud+ 的企业网络用的，你这里用不上。）

**在你这个环境下，真正还能绕过 ADH 的只剩这几条**（按重要性）：
1. **切到蜂窝数据（4G/5G）** —— 完全绕开路由器，这是最大的一条；
2. 装了带**内置加密 DNS（DoH）**的浏览器/App（Firefox 的"安全 DNS"等）—— 走 443 端口，53 端口劫持拦不住；
3. 手动装了 **VPN / 描述文件**（检查 `设置 → 通用 → VPN 与设备管理`）；
4. ~~手动改 Wi-Fi DNS~~ —— **已被 `Force-DNS-to-Router` 封堵**，无效。
